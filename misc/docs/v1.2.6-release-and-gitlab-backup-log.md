# Engineering Log: GitHub → GitLab → SVN, step by step

**Date:** 2026-06-25
**Audience:** future sessions / other developers picking this up.

`misc/RELEASE_PROCESS.md` documents the GitHub-Releases + `update-info.json` channel used for Plus/Premium self-hosted updates. It does **not** cover GitLab backup or the WordPress.org SVN channel (how the Free tier ships via the public plugin directory). This log walks through both, in the order they actually happened, with exact commands.

## Step 0 — Starting state

Two systems already existed, independently, before this work began:

- **GitHub (`origin`)** — this dev repo (`adaire-blocks-dev-main`) lives at `git@github.com:typeKibwikaIo/adaire-blocks.git`. Local `main` here is a small, self-contained lineage: `d10374c` ("first commit") → `b71a2e9`.
- **GitLab (on-prem)** — `https://gitlab-onprem01.adaire.dev/adaire-public/Adaire-Blocks.git` already held a `main` branch with 24 real release tags (`1.0.1` through `v1.2.4.alpha`), matching the tagging convention in `misc/RELEASE_PROCESS.md`. This was **not** created by this dev repo — it's almost certainly a mirror of the separate production repo `helloadaire/Adaire-Blocks` on GitHub, which `RELEASE_PROCESS.md`'s GitHub-Releases steps already reference.

So this was never "moving the project from GitHub to GitLab" — GitLab already had its own, unrelated production history. The two goals here were: (1) back this dev repo's work up onto GitLab *without* disturbing that production lineage, and (2) separately, ship a new Free-tier release (v1.2.6) through WordPress.org, which is a third system entirely (SVN, not git, not GitHub/GitLab).

## Step 1 — Add GitLab as a second remote, verify it's safe to push into

```
git remote add gitlab https://gitlab-onprem01.adaire.dev/adaire-public/Adaire-Blocks.git
git ls-remote https://gitlab-onprem01.adaire.dev/adaire-public/Adaire-Blocks.git
```
Confirmed the project exists and is reachable, and surfaced its existing branches/tags before touching anything.

## Step 2 — Check ancestry before pushing anything

```
git fetch gitlab
git merge-base main gitlab/main
```
**Returned nothing.** Local `main` and `gitlab/main` share no common ancestor — unrelated histories, not a divergent fork of the same project. This is the single most important fact for anyone touching these remotes: you cannot cleanly merge or fast-forward between them. Local `main`'s lineage is the small dev-repo history above; GitLab's `main` is the real production release lineage described in Step 0.

## Step 3 — Push dev work to GitLab as new branches, not into `main`

Because the histories are unrelated, dev work was pushed as brand-new branch names instead of into GitLab's `main`:

```
git push gitlab main:dev-main
git push gitlab adaire-block-slug:dev-adaire-block-slug
```
Result: `gitlab/main` and all 24 existing production tags were left completely untouched. The dev codebase now exists on GitLab as `dev-main` / `dev-adaire-block-slug`, fully backed up, with zero risk to production history.

## Step 4 — Open decision: promote `gitlab` to `origin` (not done yet, on purpose)

There's a standing task to make `gitlab` the default remote (`origin`). This is intentionally still pending. Local `main`'s upstream tracking is still configured against `refs/heads/main` — renaming `gitlab` → `origin` as-is would point that tracking at GitLab's *unrelated* production `main`, so the next bare `git pull`/`fetch` on `main` would either be refused (unrelated histories) or produce a confusing merge. It also overlaps with a separate, not-yet-scoped task: reconciling/migrating the production `helloadaire/Adaire-Blocks` GitHub repo into this same GitLab project.

Whoever picks this up next should choose one of:
- Rename local `main` (e.g. to `dev-main`), keep the old GitHub remote around under a new name as backup, *then* rename `gitlab` → `origin`.
- Leave `origin` / `gitlab` as two separate remotes indefinitely, pushing to GitLab explicitly when needed, until the helloadaire migration question is settled.
- Promote `gitlab` → `origin` now and rely on discipline — never run a bare `git pull`/`fetch` on `main` until lineage is reconciled.

	url = git@github.com:typeKibwikaIo/adaire-blocks.git
[remote "gitlab"]

## Step 5 — Free-build pipeline bugs (had to be fixed before any SVN release)

Separately from the GitLab work above, three real bugs in `scripts/generate-free-version.js` / `scripts/zip-generated-folder.js` had to be found and fixed before v1.2.6 could ship.

### 5.1 "0 blocks available" after a clean install (fixed 2026-06-17)
- **Root cause:** build invoked plain `wp-scripts build` instead of `wp-scripts build --blocks-manifest`, so `build/blocks-manifest.php` was never generated. `adaire-blocks.php`'s `require __DIR__.'/build/blocks-manifest.php'` then failed silently → zero blocks registered, no visible PHP error.
- **Fix:** added `--blocks-manifest` to both build invocations in `generate-free-version.js`; `verifyGeneration()` now throws if the manifest file is missing post-build.
- **If it happens again:** check whether `build/blocks-manifest.php` exists in the shipped zip before forming any other theory.

### 5.2 Double-nested install path (fixed 2026-06-18)
- **Symptom:** WP showed "Plugin file does not exist"; activate URL had a doubled path (`adaire-blocks-free/adaire-blocks-free/adaire-blocks.php`).
- **Root cause:** `Compress-Archive -Path '<stagingDir>'` (no trailing `\*`) wraps the folder inside the zip; combined with the staging folder already being named `adaire-blocks-free`, the path doubled.
- **Fix:** both scripts now use `Compress-Archive -Path '<stagingDir>\*'`; added `verifyZipStructure()` to fail loudly if a doubled-wrapper pattern is detected.

### 5.3 Backslash zip path separators (fixed 2026-06-18)
- **Symptom:** live DreamHost install triggered a fatal error on activation — `Failed opening required '.../includes/class-adaire-blocks-config.php'` — despite an apparently clean install.
- **Root cause:** PowerShell's `Compress-Archive` can write zip entry names with `\` instead of the ZIP-spec `/`. Windows extraction tolerates this; PHP's `ZipArchive::extractTo()` does not, so `includes/class-adaire-blocks-config.php` extracted as a flat file literally named `includes\class-adaire-blocks-config.php`.
- **First fix attempt was itself broken:** a `.NET`-based `normalizeZipPathSeparators()` silently normalized 0 entries because `Add-Type` didn't reliably resolve `ZipArchiveMode` in every environment. `verifyZipStructure()` correctly caught and blocked the still-broken zip, so nothing bad shipped — but the build was blocked until fixed.
- **Real fix:** removed PowerShell/.NET from the zip pipeline entirely. Both scripts now build zips in pure Node via `adm-zip` (always joins entry names with `/`). Confirmed working end-to-end on the real Windows machine on 2026-06-18 (`npm run build:free`, `npm run plugin-zip:free`).
- **Dead-end side lead (documented so it's not re-investigated):** a `0700` Unix-permission-bits theory was explored in parallel for the same symptom and never cleanly confirmed or disproven — most likely it was actually this same backslash bug being hit via a different zip than the one being inspected at the time.

## Step 7 — Publish to WordPress.org via SVN

WP.org plugins ship from an SVN repo, not git. `trunk/` is what's currently live; `tags/X.Y.Z/` is an immutable snapshot per release.

Local SVN working copy: `C:\Users\DanKibwika\adaire-blocks-svn` (checkout of `https://plugins.svn.wordpress.org/adaire-blocks/`).

1. Extract the built zip flat (no wrapper folder) and copy its contents into `trunk\`, overwriting existing files.
2. Remove anything in `trunk\` no longer shipped:
   ```
   svn delete trunk\build\fonts trunk\build\footer-block trunk\build\infogrid-block
   ```
3. Stage every add/modify/delete in one pass:
   ```
   svn add --force trunk
   ```
4. Confirm `svn status trunk` shows only `A`/`M`/`D` lines (no stray `?`/`!`) before committing.
5. Commit:
   ```
   svn commit trunk -m "1.2.6: add Header, SaaS Hero, Row, Column, About Us, Timeline, Gallery, Card Scroll, Website Footer to free build; remove deprecated footer-block/infogrid-block and local icon fonts; corrected readme block lists"
   ```
   → Committed revision **3586115**.
6. Tag via server-side copy (no local `tags/` checkout needed):
   ```
   svn copy https://plugins.svn.wordpress.org/adaire-blocks/trunk https://plugins.svn.wordpress.org/adaire-blocks/tags/1.2.6 -m "Tag 1.2.6"
   ```
   → Committed revision **3586118**.

## Step 8 — Verify it actually landed

`https://wordpress.org/plugins/adaire-blocks/` and even the raw `https://plugins.svn.wordpress.org/.../readme.txt` view can lag and keep serving the previous version's content for a while after a real, successful commit — that's a caching artifact, not a failed release. The reliable, low-latency check is the Trac changeset view:
```
https://plugins.trac.wordpress.org/changeset/3586115/adaire-blocks
https://plugins.trac.wordpress.org/changeset/3586118/adaire-blocks
```
Both showed the correct commit message, file adds/deletes, and timestamp almost immediately. Recheck the public listing 30–60 minutes later; a trivial follow-up commit can "kick" the readme parser if it's still stale after that.
